# 2026-10-30 作業記録：KIT-SEC-003 Content-LengthのないJSON本文で800KB上限を回避できる（森下担当）

ブランチ: `fix/sec-003-body-limit`（`main` の `8091710` から作成）

## 指摘（Codex の調査、Medium）

JSON 本文の上限判定が `Content-Length` に頼っていたため、chunked など長さの分からない要求で 800KB の上限を回避できた。Flask の `MAX_CONTENT_LENGTH` も未設定だった。未認証の登録・ログインの options から届く。

## 確認したこと

- `Content-Length` のない 900,009 バイトの JSON を送ると、本文をすべて読んで JSON として解析していた（表示名の長さのエラー 400 が返った）。
- Flask のテストクライアントは、入力の長さから `Content-Length` を自動で付け直す。そのため、テストではアプリを WSGI として直接呼んで再現した。
- Werkzeug 3.1.9 は `MAX_CONTENT_LENGTH` を設定しても、長さのない本文を上限で**黙って切り詰める**（例外を出さない）。設定だけでは、切り詰めた JSON が「形式が正しくない（400）」になるだけだった。

## 対応

- `MAX_CONTENT_LENGTH = 800_000` を設定した。読み込みはこの上限で止まり、メモリは上限までしか使わない。
- `json_body()` は、`Content-Length` があれば読む前に断る。ない場合は上限まで読んだ後、元の入力にまだ続きがあれば 413 `too_large` にする。解析するのは上限以内の本文だけ。
- 413 の応答を、API は JSON（`too_large`）にまとめた。
- 本番の WSGI サーバーとリバースプロキシにも、同じ以下の本文上限と読み込みタイムアウトを設定するよう、`docs/morishita.md` と `README.md` に書いた。

## 検証

- `tests/test_body_limit.py` を追加した（8件）。`Content-Length` のあり・なしそれぞれで、超過は 413 になり、読み込みが上限付近で止まること、上限以内とちょうど上限の本文は大きさで断らないことを確かめる。修正前は3件失敗した。
- pytest 192件すべて成功。
- 未対応：本番の WSGI サーバーとプロキシの設定（公開先が決まってから）。

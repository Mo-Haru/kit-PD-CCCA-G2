# 2026-10-29 作業記録：大量のアカウント作成・共有作成への対策（森下担当）

ブランチ: `feature/morishita-abuse-limits`（`main` の `722e139` から作成。PR #7 とは別）

## 背景

アカウントを大量に作られる可能性について確認した。分かった問題は次のとおり。

- 登録の回数制限は、ログインと合計して IP ごとに10分20回だけだった。1つの IP から1時間に約120アカウント作れた。
- 接続元を `request.remote_addr` のまま数えていた。プロキシの後ろでは全員が同じ IP に見え、IPv6 はアドレスを付け替えるだけで制限をすり抜けられた。
- QR 共有と家族共有は、1アカウントあたりの作成数に上限がなかった（1件最大256KB）。大量のアカウントで DB を圧迫できた。

提案した対策のうち、A の1〜3を実装した。有効な共有の上限は、ユーザーの指定で1アカウント20件にした。海外からの利用制限とボット対策の確認画面（Turnstile など）は、公開先が決まってから検討する。

## 実装

1. **新規登録の上限**
   - 接続元ごとに1日5件、サイト全体で1時間100件。
   - パスキーの検証に成功した登録だけを数える。偽の検証要求で、サイト全体の枠を使い切られないようにするため。
   - 接続元は、IPv4 はアドレス、IPv6 は /64 単位でまとめて数える（`client_key()`）。この数え方は、ほかの回数制限にも適用される。
2. **プロキシの後ろでの接続元**
   - 環境変数 `TRUSTED_PROXY_COUNT`（0〜5、既定0）を追加した。設定したときだけ、Werkzeug の `ProxyFix` で `X-Forwarded-For` を設定した段数だけたどる。
   - 0 では転送ヘッダーを信用しない。不正な値なら起動時に止める。
3. **共有の上限**
   - 有効な共有は、QR と家族共有の合計で1アカウント20件まで（`SHARE_ACTIVE_LIMIT`）。停止・期限切れ・使用済みの緊急用は数えない。超えると 409 `share_limit`。
   - 共有の作成回数は、1アカウント1日60件まで（`share_create`）。停止と作成の繰り返しも抑える。
   - 上限で断った作成は、作成回数に数えない。

## PR #8 のレビュー対応

- Codex レビュー（P2）の指摘：期限切れの共有は数えないため、次の手順を繰り返すと20件を超えられた。期限切れで枠が空く → 新しい共有を作る → 期限切れの共有の期限を延ばして有効に戻す。家族共有は期限を外す（無期限にする）ことでも戻せた。
- 対応：QR と家族共有の期限変更で、期限切れの共有を有効に戻すときだけ空きを確かめる（`require_capacity_to_revive`）。作成回数には数えない。有効なままの共有の期限変更は、これまでどおり上限と関係なくできる。
- テスト：`test_reviving_an_expired_share_needs_a_free_slot` を追加した。修正前は失敗し、修正後は成功することを確かめた。pytest 162件すべて成功。

## PR #8 のレビュー対応（オーナーのレビュー）

- **[P1] 回数制限の加算が原子的でない。** バケットを読んで Python 側で足していたため、同時の要求が同じ値を書き、回数が失われていた。並行テストで再現した（上限3回に対して7〜8回、上限2件の作成に対して6件が通った）。
  - 対応：確認と加算を、DB の条件付き `UPDATE` 1回にした。窓が切れていれば `window_started_at <= 開始` を条件に窓を作り直し、そうでなければ `hit_count < 上限` を条件に1増やす。更新できた件数（rowcount）で許可を判断する。初回のバケット作成は、窓が切れた状態の行を作り、最初の1回も同じ UPDATE で数える（`ensure_rate_bucket` / `take_rate`）。
- **[P2] 有効な共有の枠の確認と作成が原子的でない。** 19件の状態で同時に作成すると、すべてが空きありと判断していた。
  - 対応：アカウントごとのロック行（新しい表 `share_quota_locks`、移行手順 `20261029_share_quota_locks`）を、新しいトランザクションの最初の書き込みとして更新する（PostgreSQL では行ロック、SQLite では書き込みロック）。その後に件数を数え、作成回数の加算と共有の追加を同じトランザクションでコミットする。上限で断った作成や、後の検証で失敗した作成は、作成回数に数えない。期限切れの共有を期限変更で戻す処理も、同じロックを取る。
- テスト：`tests/test_abuse_concurrency.py` を追加した（ファイルの SQLite に8スレッドで同時に要求する）。既存バケットへの加算、初回のバケット作成、窓が切れた後の更新、有効な共有の枠、作成回数の上限、移行手順を確認する。修正前は失敗し、修正後は10回繰り返してすべて成功した。pytest 168件すべて成功。`main` で作った DB に新しい `init-db` をかけ、表が追加されることも確認した。
- 未確認：PostgreSQL での並行動作（手元に環境がない）。SQL は行ロックと、`READ COMMITTED` での条件の再評価を前提にしている。

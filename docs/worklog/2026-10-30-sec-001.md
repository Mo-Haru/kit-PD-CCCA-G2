# 2026-10-30 作業記録：KIT-SEC-001 端末移行の取消と移行先パスキー登録の競合（森下担当）

ブランチ: `fix/sec-001-transfer-cancel-race`（`main` の `8091710` から作成）

## 指摘（Codex の調査、High）

移行元が端末移行を取り消しても、その間に移行先のパスキー検証が進んでいると、取消の後にパスキーが登録され、状態が `target_ready` に戻る。取消 API が成功した後も、移行先は新しいパスキーでログインできた。

## 確認したこと

- 指摘の順番（登録の検証中に取消が確定する）を、決まった順番で割り込ませるテストで再現した。修正前は、取消が200の後に登録も200になった。
- 逆の順番も問題だった。取消が行を読んだ後に登録が確定すると、取消は古い行を見て移行先パスキーを無効化せずに `cancelled` を書き、移行先パスキーが有効なまま残った（修正前は、取消後のログインが200）。
- 承認・鍵束の送信・bind も無条件に書き込んでいた。取消と同時に起きると、取り消した移行が先へ進んだ（修正前は、取消の後の承認・鍵束の送信が200）。

## 対応

- 移行の状態の変化をすべて、「今の状態」を条件にした条件付き `UPDATE` 1回にした（`_move`、`_advance`）。
- 移行先パスキーの登録：パスキーと鍵の封筒を追加してから、`status = bundled`、転送トークンのハッシュ、期限内を条件に `target_ready` にする。更新できなければ、パスキーと封筒ごとロールバックして409にする。
- 取消・期限切れ：先に状態を `cancelled` / `expired` に変えてから、行を読み直して移行先パスキーを無効化する。取消の直前に登録が確定していても、取りこぼさない。すでに終わっていた場合は、その状態を返す。
- 完了：`status = target_ready` を条件に `finalized` にできたときだけ、移行元パスキーを無効化する。
- bind・承認・鍵束の送信も、それぞれの前の状態を条件にした。承認の誤り回数も、DB上で加算する（5回を超えて試せない）。

## 検証

- `tests/test_transfer_concurrency.py` を追加した（ファイルの SQLite で、関数の途中で止めて別の要求を先に確定させる）。確認したのは、登録中の取消、取消中の登録、取消後の承認・鍵束の送信。修正前は失敗し、修正後は5回繰り返してすべて成功した。

# 2026-10-30 作業記録：KIT-SEC-002 家族共有の停止と更新の競合（森下担当）

ブランチ: `fix/sec-002-family-stop-race`（`main` の `8091710` から作成）

## 指摘（Codex の調査、Medium）

`key_pending` の家族共有を更新している途中で停止が確定すると、更新の処理が最後に無条件で `status = "active"` を書き、停止した共有が再び配信される。受信者の取得 API は `status` だけを見て、`stopped_at` を確かめていなかった。

## 確認したこと

- 更新が状態を確かめた後に止め、その間に停止を確定させるテストで再現した。修正前は、更新が200になり、受信者の取得も200になった（`key_pending` と `active` の両方）。
- `status = active` のまま `stopped_at` が入った共有も、修正前は配信されていた。

## 対応

- 更新は、`active` または `key_pending`、`stopped_at IS NULL`、`current_version = expected_version` を条件にした条件付き `UPDATE` 1回にした。版・暗号文・所有者用コピーの追加は、同じトランザクションでコミットする。更新できなければ、停止済みなら409 `share_stopped`、それ以外は409 `revision_conflict`。
- 停止も「まだ停止していない」を条件にした更新にした（停止時刻を上書きしない）。
- 受信者へ配信する判定（`_deliverable`）に、`stopped_at` が空であることを加えた。

## 検証

- `tests/test_family_share_concurrency.py` を追加した（3件）。確認したのは、更新中の停止（`key_pending` と `active`）、停止中の更新、停止の記録がある共有を配信しないこと。修正前は2件失敗し、修正後は5回繰り返してすべて成功した。
- pytest 187件すべて成功。
